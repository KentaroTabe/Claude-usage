# Claude 使用量 週次レポート 設計書

- 版: 1.22
- 作成日: 2026-10-23
- 状態: フェーズ 0〜3 完了。GitHub で公開(§14)。7/21〜10/27 に終わる 15 週分のレポートを作成済み。launchd による自動作成と使用量メニューの通知を適用済み(§10)

## 1. 目的とスコープ

Claude の使用量を週 1 回、次の 2 点で報告する軽量アプリ。

1. 週次リセットまでの 1 週間の使用量の推移グラフ
2. その週にどのプロジェクトで使ったかの円グラフ

### 確定事項(ユーザー確認済み)

| 項目 | 決定 |
|---|---|
| 届け方 | 毎週のレポートを PDF にして `~/Documents/Claude_Usage` に保存し、macOS 通知で知らせる。外部サービスへは送信しない(2026-10-23 変更。当初は HTML) |
| 推移グラフの縦軸 | 上段: 週の使用量(重み付きトークンの累積。同じ図に全体を左軸、Fable を右軸で描く)。% の記録が十分な週だけ、週次上限の使用率の階段線を添える。下段: 5 時間枠ごとのトークン量(棒・左軸)と 5 時間枠の使用率(●・右軸)。トークン量の各軸の一番上は、これまでの最大値ちょうど(余白なし)。最大値が更新されたら以降のレポートから上限を上げ、作成済みのレポートは作り直さない(2026-10-23 変更) |
| 報告タイミング | 週次リセットの直後に、終わった 1 週間分を確定版として出す |
| データの粒度 | 集計の最小単位は 5 時間枠と週。1 時間ごとの使用量は扱わない(2026-10-23、ユーザー指定) |

### 対象範囲

- プロジェクト別の内訳は **Claude Code(CLI とデスクトップアプリの Code タブ)** が対象。
  プロジェクト=作業ディレクトリの概念があり、ローカルにログが残るのは Claude Code だけのため。
- 週次上限の使用率(%)はアカウント単位の値なので、claude.ai のチャット等の利用分も含んだ数字になる。
  一方、チャット分は円グラフには現れない。レポートにこの差を注記する。

### 非目標

- リアルタイム監視・ダッシュボード常駐
- 複数マシン・複数アカウントの合算
- 実際の請求額の算出

## 2. データソース(調査結果)

2026-10-23 時点、Claude Code 2.1.280 の環境で実測・確認した内容。

### 2.1 トランスクリプト(トークン量・プロジェクト)

場所: `~/.claude/projects/<cwd をエンコードした名前>/<session-id>.jsonl`
と、サブエージェント分の `.../<session-id>/subagents/agent-*.jsonl`。

- 実測: 507 ファイル、約 32 万行、記録期間 2026-07-17〜。`entrypoint` は `claude-desktop` が大半で、`cli` も混在。
- 集計に使うのは `type == "assistant"` の行:
  - `timestamp`(UTC, ISO 8601)、`cwd`、`sessionId`、`isSidechain`(サブエージェントなら true)、`requestId`、`entrypoint`
  - `message.id`、`message.model`
  - `message.usage`: `input_tokens` / `cache_creation_input_tokens` / `cache_read_input_tokens` / `output_tokens`、
    内訳 `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`

扱いの注意点(いずれも実測で確認):

| 注意点 | 対応 |
|---|---|
| 同じ応答 `(message.id, requestId)` が複数行に分かれて記録される。2,436 組では値が異なり、途中行は 0 で最後に確定値が入る | キーごとに `output_tokens` が最大の行を採用する |
| ディレクトリ名は非可逆(`PokemonChampioons_Adviser` → `PokemonChampioons-Adviser`)。worktree 用ディレクトリに本体の cwd も混在する | ディレクトリ名は使わず、各行の `cwd` からプロジェクトを決める(§5) |
| `message.model == "<synthetic>"` の行がある(256 行) | 集計から除外 |
| 生トークン合計の 97.8% がキャッシュ読込(直近 7 日) | 単純合計ではなく重み付きトークンを指標にする(§6) |

トランスクリプトは Claude Code の内部形式で、バージョンアップで変わりうる。未知のフィールドは無視し、
解釈できなかった行数をレポートの脚注に出す。

また、古いトランスクリプトが自動削除される可能性がある(`cleanupPeriodDays` は未設定。既定の保持期間は未確認)。
削除に左右されないよう、週が終わったら早めにレポートを作る(§10)。

### 2.2 ステータスライン入力(週次上限 % とリセット時刻)— 2026-10-23 に使用をやめた(§3.2)

公式ドキュメント(code.claude.com/docs/en/statusline)に記載された、ステータスラインのコマンドへ標準入力で渡される JSON:

```json
"rate_limits": {
  "five_hour": { "used_percentage": 23.5, "resets_at": 1738425600 },
  "seven_day": { "used_percentage": 41.2, "resets_at": 1738857600 }
}
```

- Pro / Max 契約のみ。セッション内の最初の API 応答の後から入る。`resets_at` は Unix 秒。
- 新しいアシスタント応答のたびに(300ms のデバウンス付きで)スクリプトが呼ばれる。
- **デスクトップアプリの Code タブではステータスラインのコマンドは実行されない**(フェーズ 0 で実機確認。§12.1)。
  - 使用率はアカウント単位なので、CLI のセッションで記録できれば、デスクトップ分も含んだ正しい値になる。
    ただし記録できるのは CLI を使ったときだけなので、デスクトップ中心の使い方では記録点がまばらになる。

### 2.3 デスクトップアプリの使用量の履歴(上限%の主な取得元)

2026-10-23 の調査で見つけた。デスクトップアプリで「これまでの使用統計」が見られることがあるのは、この記録によるものと見られる。

- 場所: `~/Library/Application Support/Claude/plan-usage-history.json`。デスクトップアプリが書く内部ファイルで、公開された仕様ではない。
- 形式(`version: 2`):

  ```json
  {"version": 2, "samples": [{"t": 1790000000000, "org": "<組織 ID>", "u": {"fh": 26, "sd": 48}}]}
  ```

  - `t` は Unix ミリ秒。`fh` は 5 時間枠の使用率、`sd` は週次(7 日)の使用率で、どちらも整数の %。
  - 秘密情報は含まない(識別子は組織 ID だけ)。
- 実測: 178 件、2026-09-23 08:32 〜 10-23 08:07 の 30 日分。記録の間隔は中央値 15 分。
- アプリのコード(`/Applications/Claude.app/Contents/Resources/app.asar`、版 3.6556.1)で確認したこと:
  - 使用量を取得するたびに 1 件追記し、そのたびにファイル全体を書き直す(起動中にも書き込まれる)。
    同じ組織の直前の記録から 4.5 分以内なら追記しない。30 日より古い記録は追記のときに消す。
  - 記録する項目と短い名前: `five_hour`→`fh`、`seven_day`→`sd`、`seven_day_opus`→`so`、`seven_day_sonnet`→`sn`、
    `seven_day_oauth_apps`→`oa`、`seven_day_cowork`→`cw`、`seven_day_omelette`→`om`、`omelette_promotional`→`op`、追加利用分→`xu`。
    **Fable の週次上限はこの中になく、記録されない**(§2.4)。
  - アプリの起動時に 1 回取得する(起動のたびに 1 件増える)。
- 記録される条件(コードとログ `~/Library/Logs/Claude/main.log` で確認):
  - アプリはバックグラウンドで 15 分ごと(トレイを触ってから 30 分間は 5 分ごと)に使用量を取得する。
  - ただし「メニューバーの Claude アイコンを**右クリック**して使用量のメニューを開く」か、そのメニューの「更新」を押してから
    24 時間以内のときだけで、過ぎると止まる
    (`[plan-usage] config: poll requires tray open within 86400000ms` / `background poll paused: tray not opened recently`)。
    - 24 時間という値はアプリがサーバーから受け取る設定(`pollRequiresTrayOpenWithinHours`)。
    - 最後に開いた時刻は `~/Library/Application Support/Claude/config.json` の `planUsageLastTrayOpenAt` に保存される。
      2026-10-23 時点でこのキーはなく、トレイの使用量メニューを開いた記録はない。
    - アイコンの左クリック(クイック入力が開く)や、アプリのウインドウ内の使用量の表示は、この条件に数えられない。
      10/23 にウインドウ内の表示を何度か開いたが、取得は再開しなかった(ログに `background poll resumed` が出ない)。
  - 10 月に入ってから記録がまばらなのはこのため(10/4 以降は 1 日 0〜7 件。ほぼ起動時の 1 件)。
- 分かること:
  - 5 時間枠: `fh` が下がった所がリセット。リセット直前の値は、下がる直前の記録として取れる(取得間隔 15 分以内)。
    - 例: 9/29 13:16 に 0% → 13:35 に 18% → 17:58 に 67% → 18:13 に 0%。
    - 枠は最初に使った時刻の「時」(13 時)から 5 時間(18 時)と見られる。2 例からの推定で、未確認。
    - このため、リセット時刻に合わせて自前で取得しに行く必要はない。レポートを作るときに「下がる直前の記録」を拾えばよい。
  - 週次: `sd` が下がった所が週次リセット。
    - 9/29(火)18:58 → 19:13 の間に 57% → 0%。火曜 19:00 の周期と一致する。
    - 10/4(日)14:35 → 14:42 の間にも 66% → 0% に下がっている。これは手動のリセット(ユーザーによる)。
      手動のリセットもありうるため、週の区切りは固定周期を前提にせず、観測した下降から組み立てる(§4)。
- 使い方: `cu report` がレポートを作るときに直接読む。30 日で消えるため、週が終わったら早めに作る(§10)。
- statusLine の記録係(§2.2)は 2026-10-23 に削除した(§3.2)。

### 2.4 Fable の使用量(週次上限の % の代わり)

- デスクトップアプリの使用量表示(Claude からは `get_usage` で読める)には「Weekly · Fable」(10/23 14:08 時点で 13%、
  リセットは全体の週次と同じ 10/27 19:00)が出る。
- しかし Fable の % の取得元になるものはない。
  - plan-usage-history.json には記録されない(§2.3。記録する項目の対応表に Fable がない)。
  - アプリは最新の取得結果をメモリにだけ持ち、ファイルには残さない(コードで確認)。
  - statusLine の `rate_limits` にもモデル別の項目はない(ドキュメントで確認)。
- **決定(2026-10-23、ユーザー): Fable はトークン量で表す。**
  - トランスクリプトの `message.model` が設定 `report.models` の先頭(`Fable = "claude-fable"`)に一致する応答の重み付きトークンを、
    5 時間枠ごとに集計する(`WindowBucket.by_model`)。モデル名の判定は `metrics.model_group`。
  - グラフは、週の始まりを 0 とした累積(§9)。
    KPI に合計と全体に占める割合とその週の倍率(推定値か既定値か)、5 時間枠ごとの表に Fable の列を出す。
  - 不採用にした案: Claude のスケジュールタスクで `get_usage` を定期的に読む(毎回使用量を消費するため)。
- **2026-10-28 追記**: Claude Code(CLI)にも、モデルに問い合わせずに /usage の値を返す制御要求 `get_usage` があり、
  Fable の週間上限の % が取れることが分かった。定期実行で記録し、使用率のグラフに重ねる(§2.13)。
  使用量(API 換算額)のグラフと KPI はそのまま残す。

### 2.5 トレイの使用量メニューを開かない場合の影響

使用量メニューは、画面上部の**メニューバー**にある Claude のアイコンを右クリックしたときに出る(Dock のアイコンの右クリックではない)。
アイコンは設定 `menuBarEnabled`(既定でオン)のときにアプリが作る。10/23 08:07〜08:31 に取得の処理が動いていたので、
アプリ側ではアイコンを作っている。

**確認済み(2026-10-23 15:22)**: メニューバーの Claude のアイコンは元から表示されていた(macOS の許可も済み)。
アイコンから開くメニューの「プランの使用制限」が、ここでいう使用量メニュー。
表示項目は「5 時間制限」「週間・すべてのモデル」「週間・Fable」(% と次のリセットまでの時間)、「更新(◯時間前に更新)」「使用量設定…」。

- 開いた直後に `config.json` の `planUsageLastTrayOpenAt` が 15:22:47 で保存され、plan-usage-history.json に 1 件追記された
  (15:22、5 時間枠 38%・週次 32%)。
- 5 分後の 15:27:47 にログに `[plan-usage] background poll resumed` が出て、次の 1 件が追記された(5 時間枠 39%・週次 32%)。
  コードのとおり、開いてから 30 分は 5 分ごと、その後は 15 分ごとに記録が続き、24 時間で止まる。
  → **1 日 1 回このメニューを開けば記録は止まらない**(実機で確認)。
- メニューには Fable の週次の % も出るが、plan-usage-history.json には記録されない(§2.3・§2.4 のとおり)。
- アカウントメニュー(左下)の「使用量」はウインドウ内の表示で、取得の条件には数えられない(§2.3)。

以下は、アイコンが見当たらなかった時点で、公式ドキュメントと有志の調査を調べた結果(2026-10-23):

- Anthropic の公式ドキュメント(support.claude.com)に、メニューバーやトレイの使用量表示の説明は見つからなかった
  (Mac のクイック入力の記事だけ。https://support.claude.com/en/articles/12626668-use-quick-entry-with-claude-desktop-on-mac)。
- macOS 26 では、他社アプリのメニューバーのアイコンは「システム設定 > メニューバー」下部の
  「メニューバーでの表示を許可」(英語版 Allow in the Menu Bar)で許可するまで表示されない
  (https://www.techradar.com/computing/mac-os/what-is-the-macos-menu-bar-heres-how-new-macbook-neo-users-can-get-the-most-out-of-apples-app-control-bar 、
  https://forum.parallels.com/threads/asking-how-to-keep-toolbox-icon-on-menu-bar.369594/ )。
  - Claude のアイコンがこの仕組みで消える報告がある(macOS 26.3。起動直後にアイコンが破棄される)。
    https://claudeissues.com/issue/42019-claude-for-desktop-menu-bar-icon-blocked-on-macos-26-statuskit-trackedapplicatio
  - ユーザーの環境(macOS 26.5.1)では許可済みで、アイコンも表示されていた。原因ではなかった(見落とし)。
  - 報告にある「設定ファイルを sudo で書き換える」回避策は、システムが管理するファイルを書き換えるため採らない。
    システム設定の画面で許可し、Claude を再起動するのが筋。
- Windows 版では、右クリックで使用量が出る機能がアップデート(1.24012.9、2026 年 8 月)で消えたという報告があり、
  「対応予定なし」で閉じられている。使用量は「設定 > 使用量」かチャットの `/usage` でしか見られなくなった、とある。
  https://claudeissues.com/issue/85343-bug-regression-claude-desktop-right-click-tray-icon-no-longer-shows-subscription
  - Mac 版(3.6556.1)のコードには右クリックの使用量メニューが残っているが、同じように消える可能性がある。
    このアプリはトレイの記録だけに頼らない(トークン量のグラフは影響を受けない)。
- 有志のメニューバー用アプリ(ClaUse Bar、Claude Usage Bar など)は、claude.ai にログインして使用量を取得する。
  ログイン情報を扱うため、このアプリの取得元には採らない(§2.7)。

開かない場合、上限%の記録はアプリの起動時の 1 件ずつに近くなる。実データ(週は火曜 19:00 区切り)での比較:

| 週 | plan-usage-history の記録数 | 5 時間枠の数(Claude Code の利用から推定) | うち 5 時間枠%の記録がある枠 |
|---|---:|---:|---:|
| 9/22〜9/29(取得が動いていた) | 111 | 11 | 10 |
| 9/29〜10/6 | 58 | 20 | 4 |
| 10/6〜10/13(取得が止まっていた) | 5 | 13 | 2 |
| 10/13〜10/20 | 3 | 12 | 1 |
| 10/20〜(10/23 15 時まで) | 1 | 8 | 0 |

レポートへの影響:

- 週次上限の使用率: 階段線が数点だけになる。「最終」の値はリセット直前ではなく、最後にアプリを起動したときの値になる。
- 週の区切り: 記録の間が何日も空くと、手動リセットや週次リセットがいつあったか分からない、または見落とす。
  - 例: 10/4 20:19(16%)の次の記録は 10/9 17:36(65%)。この間の 10/6 19:00 にリセットがあったかどうかを記録から判断できない。
- 5 時間枠: ●(リセット直前の使用率)がほとんどの枠で出ない。枠の区切りもトランスクリプトからの推定になり、
  claude.ai での利用で始まった枠は分からない。
- 影響しないもの: 5 時間枠ごとのトークン量の棒、プロジェクト別、Fable の使用量(どれもトランスクリプトから集計するため)。

### 2.6 トレイを開く働きかけ(記録を止めないため)

記録が止まらないように、このアプリから 1 日 1 回デスクトップアプリに働きかけられるかを 2026-10-23 に試した。

| 方法 | 結果 |
|---|---|
| `claude://` のディープリンク | 使用量やトレイを開くリンクはない(アプリ内のリンクは新規チャット・Code・Cowork 関係だけ) |
| AppleScript(System Events)でメニューバーのアイコンを操作する | `osascript` に「アクセシビリティ」の許可がなく拒否された(エラー -25211)。許可はシステム設定の変更なので、ユーザーの判断が必要 |
| 同上(許可を出した場合) | 未確認。アイコンの右クリックに当たる操作(`AXShowMenu`)が、アプリの「右クリック」の処理を呼ぶかは試せていない。呼べてもメニューが一瞬画面に開く |
| `config.json` の `planUsageLastTrayOpenAt` を書き換える | 採らない。他のアプリの内部設定を書き換えることになるうえ、アプリは起動時にしか読まないため効果もない |
| 通知で知らせる(記録が止まったら、使用量メニューを開くよう促す) | 許可は不要。開くのはユーザー。**採用**(§10) |

- 補足: トレイの条件は、使用量を見ていない人のためにアプリが取得を止める、意図された動作(サーバーから受け取る設定)。
  自動で開く方法は、毎日人が開くのと同じ結果になるが、アプリの意図を回避することにもなる点に注意する。

### 2.7 採用しなかった取得手段

| 手段 | 不採用の理由 |
|---|---|
| hooks の入力 JSON | ドキュメント上、`rate_limits` 相当のフィールドがない |
| トランスクリプトの `quotaLimits` | 上限に達して拒否されたとき(`status: "rejected"`)しか記録されない(実測 122 行、すべて `five_hour`)。リセット時刻の補助情報としてのみ使う |
| 非公開の OAuth 使用量 API | 公開されていない API で、Keychain の OAuth トークンを読む必要がある(秘密情報の扱いになる) |
| claude.ai の使用量 API をデスクトップアプリのログイン情報で直接呼ぶ | Cookie などのログイン情報を扱う必要がある。デスクトップアプリ自身が取得した結果(§2.3)を読めば足りる |
| デスクトップアプリの Local Storage | 使用率と次回リセット時刻の最新値が 1 件あるだけで、履歴はない |
| Claude の `get_usage`(デスクトップアプリ内の Claude から読める使用量) | アプリ内の Claude からしか呼べず、launchd のジョブからは取得できない。→ 同じ名前の Claude Code(CLI)の制御要求は launchd から使えるので採用した(§2.13) |
| `~/.claude/stats-cache.json` | 2026-07-22 で更新が止まっており、プロジェクト情報もない |

### 2.8 週次上限の使用率と使用量が噛み合わない理由(2026-10-23 調査)

ユーザーの指摘: 先週(10/13〜10/20)は週次上限(全モデル)に達したが、レポートの使用量はそれほど多く見えない。
調査に使ったスクリプトは使い捨てで、結果だけをここに残す。

1. **モデルによって、同じトークン量でも上限の消費が大きく違う**(確認済み、推定値)
   - デスクトップアプリの記録が 15 分ごとにあった 9/23〜10/23 の 56 区間で、「週次%の増分」を
     「その区間の Claude Code のモデル別の重み付きトークン」で最小二乗に当てはめた。
   - 1pt(週次上限の 1%)あたり: Fable 約 108 万、Opus 約 428 万。**Fable は Opus の約 4 倍の速さで上限を減らす**。
     Sonnet・Haiku は量が少なく推定できなかった。大半の区間で、見積もりと実際の差は数 pt 以内。
   - このアプリの重み付きトークンは、トークンの種類(入力・キャッシュ・出力)の比だけを掛け、モデルの差を入れていない(§6)。
     そのため、Opus の多い週はトークン量が多く見え、Fable の多い週は少なく見える。
2. **Claude Code 以外の利用は数えていない**(確認済み)
   - 週次上限は claude.ai のチャット、ほかの端末、クラウドのセッションなどとも共通。これらはこの Mac の会話ログに残らない。
     Cowork の会話ログもローカルには見つからなかった(`local-agent-mode-sessions` などに jsonl なし)。
   - 先週は、10/19 17:55 の記録が 69% だったのに対し、Claude Code の分を 1 の換算で見積もると約 33%。
     週全体でも見積もりは約 49% で、上限(100%)との差の約 50pt は、この Mac の Claude Code 以外の利用と考えられる(未確認)。
   - 先週の会話ログには、週次上限で応答が拒否された記録(`quotaLimits` の `seven_day`)がない。
     上限に達したのも Claude Code 以外の利用中だった可能性がある(未確認)。
3. **先週は使用率の記録が途中で止まっていた**(確認済み)
   - 記録は 10/19 17:55 の 69% が最後で、その後に 100% に達した。レポートの「週次上限の使用率」は最後の記録の値なので、
     実際より低く見えていた。→ KPI の表記を「(最終)」から「(最後の記録)」に変えた。
4. **時期によって換算が変わる**(確認済み、原因は未確認)
   - 1 の換算を 8/25〜9/8 の週に当てはめると 115〜204% になるが、その週に週次上限で拒否された記録はない。
     当時は同じトークン量でも消費が小さかった(モデルの版の違い、上限の大きさや数え方の変更など。原因は不明)。
   - したがって、トークン量から週次の使用率を正確に再現することはできない。トークン量は「どこで・どのモデルで使ったか」の
     比較に使い、上限に対する状況は使用率の記録(§2.3)で見る。

**決定(2026-10-23、ユーザー)**: 重み付きトークンにモデルの倍率を入れる(§6)。倍率は §2.9 の調査に基づき、
Fable は「~2×」が公表されていた期間は 2、それ以降は 1 の推定値の 4。上限の大きさ(トークン量)が時期で変わるのは前提とし、
トークン量から週次の使用率を再現することはしない。Claude Code 以外の利用は §2.10 の方法で割合として加える。

- 補足(2026-10-23): 違いが出るのは、モデルごとにキャッシュ読み込みの単価の比が違う Fable 5.1(入力の 0.025 倍)と
  Opus 5.5(0.05 倍)だけ。Fable 5・Opus 5・Opus 4.8 は単価の比が共通の重みと同じ(0.1 倍)で、単価で重み付けしても
  共通の重みに「Fable 2 倍(単価の比 $10/$5)」を掛けたのと同じになる。実際、7/28〜9/1 の週の Fable の消費率のばらつきは
  どちらの重みでも同じで、ばらつきが縮むのは Fable 5.1 の週(9/15〜10/13: 共通の重みで 2.2 倍の幅 → 単価で 1.27 倍の幅)。

### 2.12 単価の自動の更新(2026-10-23)

ユーザーの要望: 単価ベースにするなら、新しいモデルの追加や単価の変更に自動で対応したい。

- 取得元: Claude Code が会話ログに残す `cost-state` 行(セッションの累計の、モデルごとのトークン数と `costUSD`)。
  Claude Code は自動で更新され、自分の単価表で費用を計算しているので、新しいモデルや単価の変更がここに現れる。
  ローカルのファイルだけで済み、外部のサービスへの依存を増やさない。
- 確認(実データ 227 件の増分): Claude Code の費用は公式の単価とほぼ一致した(書き込みを 1 時間として計算)。
  Fable 5.1 13/13、Opus 5 54/55、Opus 5.5 71/80(残りは 5 分の書き込みを含む記録)、Sonnet 5 37/37、Haiku 4.5 34/34。
  Haiku 5.5 は 7 件中 6 件が合わない(長いプロンプトの割増と考えられる。未確認)。
- 応答ごとに Claude Code の費用を割り振る方法は採らなかった: `cost-state` の累計は応答の合計と 87 件中 36 件しか合わない
  (応答に残らない内部の呼び出し(Haiku など)を含み、セッションの再開で数え直すこともあるため)。
- 方法(`metrics.learn_prices`): 費用の記録の増分を単価表(と、これまでに推定した単価)と比べ、
  MATCH(書き込みを 1 時間として 3% 以内)/ NEAR(5 分〜1 時間の幅の中。書き込みの多い記録は別の単価とも合いうるので数えない)
  / MISS に分ける。最後の MATCH より後の MISS が 3 件以上なら、それらから単価を推定し(公式の単価と同じ構造
  ── 出力 = 入力×5、書き込み = 入力×1.25・×2 ── を仮定して、入力とキャッシュ読み込みの単価を最小二乗で求める)、
  その最初の記録の時刻からの単価として `state.json` の `prices` に保存する。既定の条件は `[metric.price_learning]`。
- 推定した単価や系統の代わりの単価で計算した週は、レポートの注記に単価を書く。
- 実データで試した結果、単価表に足す単価はなかった(表の単価と合っている)。
- 限界: 新しいモデルは、そのモデルを使ったセッションが `cost-state` を書くまで(多くは同じ日のうち)系統の代わりの単価になる。
  `cost-state` は 5 分と 1 時間の書き込みを分けないので、書き込みの多い記録では単価の違いを見分けにくい。

### 2.14 開発時間(2026-11-01)

ユーザーの要望: 開発に使った時間も出す。

- 計算(`metrics.active_time`): 会話ログの応答の時刻を並べ、間隔が `[report] dev_time_gap_minutes`(15 分)以内なら続けて作業して
  いたとして足す。長い間隔は作業の切れ目として数えない。応答の時刻だけを使い、本文は読まない。サブエージェントの応答も含める
  (親のセッションが待っている間も作業は続いているため)。
- 週の合計は全セッションをまとめて計算し、並行したセッションは 1 回に数える(実際に過ぎた時間)。プロジェクト別はそのプロジェクトの
  応答だけで計算するので、並行した分は重なり、合計は週の値より大きくなることがある。
- 間隔の 15 分は、よく使われる区切りの値(WakaTime の既定値など)に合わせ、ユーザーが確定した(2026-11-02)。区切りで値はかなり変わる
  (10/27 に終わる週、サブエージェントを除いた試算: 5 分 13.5 時間・15 分 19.1 時間・30 分 25.7 時間・60 分 32.5 時間)。
  絶対値よりも、同じ区切りで週やプロジェクトを比べるための値として見る。
- 限界: Claude Code に関係する時間だけで、Claude Code の外での作業(自分でのコーディング・確認・調査)と Cowork・チャットは含まない。
  デスクトップアプリから自動で動いた分は区別できない(`entrypoint` はほぼすべて `claude-desktop`。スケジュール実行があるかは未確認)。
  長い処理を人が待っている間も、応答がなく 15 分を超えれば数えない。
- 別案: `cost-state` の `totalAPIDuration`・`totalToolDuration`(Claude が処理していた時間)は、セッションの累計で時刻がなく、
  並行分も重なるので使わなかった。

### 2.15 活動の再生画面(2026-11-02)

ユーザーの要望: 全期間の記録について、そのときのプロジェクト・セッションを表示し、よく動いているものほど明るく(赤く)し、関係のある
セッションを連結して近づけ、全期間と個別の期間で再生できる画面。**見て楽しむためのものなので見た目に気を使う**(ユーザーの指定)。

**調べたもの**(方向性を決めるため):
- Gource(リポジトリの履歴の再生): 光のにじみ(bloom)、活動を追うカメラと全体を見るカメラの切り替え、動きのない時間の自動スキップ、
  消えていくファイル、弾むような動き(elasticity)。
- code_swarm(Ogawa の「organic information visualization」): 要素が光って飛び、関係のあるものが寄り集まり、止まると名前が消える。
- GitHub の地球儀: 後光・本体・弧を層に分けて重ね、弧が伸びて消える動きで出来事を見せる。
- Obsidian のグラフの再生: 要素が増えて育っていく様子そのものが見どころ。速さの変更と一時停止の要望が多い。
- Agent Flow など Claude Code のセッションの可視化: 実務の監視向けで、楽しむためのものではない。
- 加算合成(canvas の `lighter`): 重なった光が白に近づき、目が強い光を見たときの感じに近い。

**方向性**: 初めの案(固定の位置に平らな丸を置く静止画に近い図)には動きと層がなかった。「暗い宇宙に浮かぶ星雲」にした。
プロジェクト = 星雲、セッション = 星、応答 = 火花、関係 = 星座の線。

**実際に見たユーザーの修正(2026-11-02)**:
- カメラは小刻みに動かさない。一度広がった視界はそのままでよく、中心も頻繁に動かさない。→ それまでに生まれたものが入る範囲へ広がるだけにした
  (追跡カメラと切り替えのボタンは外した)。ホイールとドラッグで手動で動かせ、ダブルクリックで戻す。
- タイトルとエンディングはいらない。→ 外した。
- 星雲が最初から変わらないので、成長していく感じを出す。→ 下の「星雲」のとおり、ガスが中心から広がっていく。
- 星雲を天体望遠鏡で見たときのように高画質にする。→ WebGL で高解像度の画像を生成するようにした。
- 背景の色は変えず、常に暗いままにする。→ 時刻で色が変わる空を外した。
- 反応がない時間の早送りは機能としてあってよいが、既定にしない。→ 「静かな時間を飛ばす」の切り替えにして、既定はオフ。
  早送りが既定でなくなったので、標準の速さを 1 秒 24 刻み(1 日が約 4 秒、1 週間が約 28 秒、全期間が約 7 分)にした。

**2 回目の修正(2026-11-03 ユーザーの指定)**:
- 画面は今後の Claude の使用に合わせて変わる想定にする。→ 配置・種類を記憶し、大きさは絶対の式にし、定期実行で作り直す(下の「今後の使用への追従」)。
- 異なるプロジェクト同士が触れないようにする。→ 星雲を互いに重ならないよう置き、星は自分の星雲の中に置く。
- 活動の爆発が固定された位置で起きるのがおかしい(星雲が平面に広がったため)。→ 星は星雲の中をゆっくり回り、活動の光はガスの広がりの中のあちこちで灯る。
- 星雲がどれも色違いに見える。→ 形を 8 種類に分け、種類ごとに色の付け方も変えた。
- 色付けの見直し。→ 実在の天体の配色に寄せ、各色を別々に飽和させて白く濁っていたのを、色を保つ飽和に変えた。

**3 回目の修正(2026-11-03 ユーザーの指定)**:
- 星雲の種類をプロジェクトの種類と対応付ける(種類分けに自信がなければ聞く)。→ 分け方を確認した(下の「プロジェクトの種類」)。
- 生まれたてのプロジェクトは似た姿にして、徐々に分かれていく。→ どれも同じ「生まれたての姿」で生まれ、使うほど種類の姿へ移り変わる。

**プロジェクトの姿**(2026-11-03 ユーザーの決定と指定):
- 初めは種類を 1 つに決めて形を対応させた(作るもの別: ゲーム → 渦巻 / アプリ → 環状星雲 / Web → 散光星雲 / AI・データ → 双極星雲 /
  道具・自動化 → 創造の柱 / 試作 → 生まれたての姿)。その後のユーザーの指定「種類をもっと細かく、または連続的な状態として持つ。
  全く同じものはない感じで」により、種類を 1 つに決めず、連続した特徴を混ぜて姿を作るようにした。
- 作るものの比率(`activity.composition`): プロジェクトのフォルダのファイル構成を、名前と拡張子だけで見る(中身は読まない。node_modules などには入らない)。
  6 つの方向(ゲーム・アプリ・Web・AI とデータ・道具と自動化・画像と文書)ごとに、拡張子の数の対数と目印(Unity のフォルダ、Xcode のプロジェクト、
  package.json など)を足し、合計 1 の比率にする。フォルダは、最も多く使った作業ディレクトリからリポジトリの一番上までさかのぼって選ぶ(`project_roots`)。
- 設定 `[activity.project_kinds]` で、比率を半分ほど寄せられる。判定に迷ったものはユーザーに確認して入れた:
  PokemonChampioons_Adviser → AI・データ(Web の画面もあるが分析が主役)、PirateGame → AI・データ(ゲームを題材にした機械学習)、
  daily-scout → 道具・自動化(毎日の自動実行が主役)。
- 使い方の特徴(`activity.usage_traits`。会話ログの記録から、どれも 0〜1): 並行の作業(サブエージェントの分の割合)、休んでいた時間
  (最初から最後までのうち使わなかった日の割合)、使い方の波(日ごとの使用量のばらつき)、温かい色に寄せるモデル(Fable)の割合、
  勢い(使った日の 1 日あたりの使用量)、セッションの数。
- 形の混ぜ方(`activity.nebula_shape`): 8 つの形の成分の重みを、作るものの比率(設定 `[activity.categories]` で方向 → 形)と、
  並行の作業 → 超新星残骸の細い筋、休んでいた時間 → 暗黒星雲の影 から作り、強調(1.5 乗)して主な形が読み取れるようにする。
  生成の手間を抑えるため、重みの大きい 3 つまでを描く。シェーダーは各成分の色と広がる順番を重みのとおりに足す。
- 見え方の調整: 乱れ ← 使い方の波、塵 ← 休んでいた時間、細い筋 ← 並行の作業、色合い ← Fable の割合(多いほど温かい)、
  埋もれた星の数 ← セッションの数、芯の明るさ ← 勢い。向き・つぶれ・色合いの細部は名前から決まる数で変える。
  比率と特徴は連続した値なので、同じ姿の星雲はできない(フォルダがなく特徴もない小さな試しでも、名前から決まる数で違う形になる)。
- 生まれたての姿: 塵の繭に包まれた若い星(共通の 1 枚の画像を、プロジェクトごとに向きだけ変えて描く)。そのプロジェクトの姿への移り変わりは
  使った API 換算額の対数で進み、`mature_usd`($300)でなりきる。小さな試しは生まれたての姿に近いまま。
  ファイル構成や使い方が変われば姿も変わる(今後の使用に合わせて変わる)。
- 衰え: 最後の応答からの時間で、`dormant_days`(7 日)から `dead_days`(30 日)にかけて、色が抜けて暗いくすんだ赤茶になる。名前も薄くなる。
- 星の詳細には、そのプロジェクトの作るものの比率(例「AI・データ 6 割・画像・文書 2 割」)を出す。

**星雲**(`assets/activity.js`。WebGL2 はブラウザの標準機能で、追加の依存はない):
- 2D の Canvas では画質が足りないので、起動時に WebGL のシェーダーで星雲ごとの画像を生成する(星雲の半径に応じて 512〜2048 ピクセル四方)。
  共通の下地は、ゆるやかにねじった雑音のガスの濃淡・暗い塵の帯とその縁の光・形の崩れた外周・埋もれた星と回折の光条。強くねじると大理石のような模様になるので、弱くしている。
- 形は 8 種類で、実在の天体を手本に、種類ごとに形の作り方と色の付け方を変える:
  散光星雲(干潟星雲: 深紅のガスと青い心臓部)/ 創造の柱(わし星雲: 青緑と金の空に暗い柱)/ 環状星雲(リング・らせん星雲: 中は青緑、外は赤)/
  双極星雲(バタフライ星雲: 腰のくびれと両翼)/ 超新星残骸(網状星雲: 赤と青の細い筋)/ 反射星雲(プレアデス周辺: 青い光と明るい星)/
  渦巻(アンドロメダ: 金の芯、青い腕、桃色の星形成領域)/ 暗黒星雲(馬頭星雲: 赤い幕に黒い影)。
  形はこれらを混ぜて使う(上の「プロジェクトの姿」。初めは種類が偏らないよう順に割り当て、次にプロジェクトの種類で 1 つ選び、4 回目の修正で混ぜる形にした)。
  向き・つぶれ・色合いは名前から決まる数で少しずつ変える。
- 色は、明るさだけを飽和させて色相を保つ(各色を別々に飽和させると白っぽく濁るため)。
- 生成は 256 ピクセルのタイルに分け、1 コマに 10 ミリ秒ほどずつ、早く生まれるプロジェクトから進める(Apple M1 で全 704 タイル、合計約 6.5 秒)。
  生成が終わるまでの星雲は描かれないが、再生は止めない。
- 成長: 画像の透明度の欄に「その点までガスが広がる順番」を持たせ、毎コマ、そのときの使用量の半径 ÷ 今の半径(`growthOf`)まで切り抜いて描く。
  生まれたときは小さな芯だけで、使うほど中心から外へ広がる。動いている間は明るくなる。
- 活動の光: 同じ場所で爆発させず、星のまわりのガスの広がりの中のあちこちで光が灯って消え、小さな火花が散る(星形成領域のように)。
- 星の動き: 星は星雲の中を約 10 日で 1 周する。位置は再生の時刻だけで決まるので、巻き戻しても同じ場所に出る。関係のある星同士の距離は保たれる。
- WebGL2 が使えない環境では星雲は描かれない(ほかの層は動く)。

**画面**(`render/activity.py`・`assets/activity.js`・`activity.css`。外部のものを読まない 1 ファイルの HTML。約 100 KB):
- 層(奥から): 遠い星(静止)→ 星雲(WebGL)→ 関係の線 → にじみ → 星 → 活動の光・火花 → 波紋 → 名前。
- 演出: 星の誕生(弾む + 波紋)、新しいプロジェクトの誕生(大きな波紋 + 名前)、活動の光、関係の線が伸びる、
  動いている組の間を光が行き来する、消える星が星雲へ溶ける、星雲の成長。
- 再生: 全期間 / 見どころ(応答の多い 3 日)/ 週 / 時間軸のドラッグで選ぶ範囲。標準は 1 秒 24 刻み(0.5〜4 倍速)。
  「静かな時間を飛ばす」をオンにすると、動きのない時間を最大 36 倍で早送りする。日ごとの応答数の棒を時間軸に重ねる。
- カメラ: 視界は広がるだけで狭まらない(期間を選び直すと、その始まりから広げ直す)。
- 名前は星雲に重ならないよう下に書く。星とプロジェクトの中心を結ぶ線は外した(星が星雲の中にあるので要らない)。
- 星に載せると詳細を出し、関係のある星以外を暗くする。操作しないと操作部が薄くなる。
- 性能: にじみは縮小した層に描く。再生の速さはコマ落ちしても変えず、遅い環境では解像度を自動で下げる。
- 画面の大きさが 0 の間(隠れた枠の中など)は描かずに待ち、大きさが付いたら描き始める(2026-11-03)。以前は大きさ 0 の
  にじみの層を描こうとして例外になり、描画の繰り返しが止まって、あとで大きさが付いても再生が進まなかった
  (公開したデモを、隠れた状態のブラウザ画面で開いて見つけた)。
- 自動更新: 上の「今後の使用への追従」のとおり。失敗はログだけ。全期間の会話ログを読むので 1 回 40 秒ほどかかる(2026-11-02 時点)。

ブラウザ画面が隠れた状態でしか動かせなかったので、WebGL にしてからの再生のなめらかさは未確認。

## 4. 週の区切り

- 週は設定 `week.reset_anchor`(2026-10-27 19:00 JST)から `cycle_days`(7 日)ごとに区切る。つまり火曜 19:00 〜 翌週火曜 19:00。
  - 根拠: 9/29(火)19:00 の週次リセット(§2.3)と、デスクトップアプリが示す次回リセット(10/27 19:00)が 7 日周期で一致する。
  - 9/22 以前は記録がなく、当時も同じ周期だったかは未確認。各レポートの注記に「7 日周期として計算」と書く。
- 手動のリセット(10/4 のような)では週を区切らない。週の途中で週次の使用率が下がった箇所を注記に書く
  (週次上限のグラフでは線が 0 に落ちる)。
- レポートを作るのは週が終わった後(終わり ≤ 現在)。会話ログもデスクトップの記録も 1 件もない週は作らない。
- 5 時間枠: 前の枠が終わった後、最初に使った時刻の「時」から 5 時間(設定 `window_hours`)。Claude Code の利用から推定する。
  リセット直前の 5 時間枠の使用率は、枠の中で記録された値の最大値(枠の中では増える一方のため)。

## 5. プロジェクトの判定

1. セッションを始めたディレクトリを求める。会話ログのフォルダ名は、始めたディレクトリの英数字以外を `-` にしたもの。
   応答時の cwd とその上位のうち、同じ変換でフォルダ名に一致するものを使う(なければ cwd のまま)。
   - セッションの途中でサブディレクトリに移っても、同じプロジェクトにまとまる。
     例: `watch_only/8bar-digger` → `watch_only`、`PokemonChampioons_Adviser` の中の別リポジトリ `pokemon-showdown` → `PokemonChampioons_Adviser`。
2. `projects.aliases`(正規表現 → 名前)に一致すれば、その名前。
3. worktree 部分を除く(`projects.worktree_patterns`。例: `/.claude/worktrees/<名前>`、`<repo>-worktrees/<名前>`)。
4. 上位へたどり、`.git` を持つ最も近いディレクトリの名前。`.git` がファイル(linked worktree)なら、`gitdir:` から本体のリポジトリ名を求める。
5. どれにも当たらなければ末尾のディレクトリ名。

実データ(7/17〜10/20)では 19 のプロジェクトに分かれた。

## 6. 指標: API 換算額 × モデルの倍率(2026-10-23 に単価ベースへ変更)

生のトークン合計はキャッシュ読込が 97.8% を占め、実際の負荷を反映しない。そこで、各応答のトークン数にそのモデルの API の単価を
掛けた「API 換算額」(ドル)に、モデルの倍率を掛けたものを、時系列・5 時間枠の棒・円グラフ・Fable の使用量の共通の指標にする。

```
使用量 [ドル] = (input × 入力の単価 + cache_write_5m × 5 分書き込みの単価 + cache_write_1h × 1 時間書き込みの単価
               + cache_read × キャッシュ読み込みの単価 + output × 出力の単価) ÷ 100 万 × モデルの倍率
```

- 単価は設定 `[metric.prices]`(公式の単価、2026-10-06 時点)。モデル ID の先頭で探し、長く一致するものを使う。
  表にない新しいモデルには系統の代わりの単価("claude-opus" など、各系統の最新)を使い、費用の記録から単価が分かれば
  自動で置き換える(§2.12)。
- 2026-10-23 まで(1.6 版)は、全モデル共通の重み(入力 1・書き込み 1.25/2・読み込み 0.1・出力 5)の「重み付きトークン」だった。
  ユーザーの判断で単価ベースに変えた(理由は §2.11: Fable 5.1・Opus 5.5 はキャッシュ読み込みが安く、共通の重みでは
  4 倍・2 倍に多く数えていた。Fable 5・Opus 5 までは共通の重みに単価の比を掛けたのと同じ)。
- モデルの倍率は、単価の差を超えて上限を減らす分(単価に対する倍率)。設定 `[metric.model_factors]` に期間ごとに置く。
  Fable は 9/1 に終わる週まで 1(公表の「~2×」は Fable 5 と Opus の単価の比 $10/$5 と同じ)、それ以降 2
  (9/23〜10/23 の記録を API 換算額で当てはめた約 1.95)。ほかのモデルは 1。
  (共通の重みのときの既定値 2・4 に当たる。)レポートに出す既定値は、週の最後の時点の値。
- 週ごとの倍率: その週の使用率の記録(または画面の値)から推定できれば、その週はその値を使う(§2.11、`[metric.weekly_factor]`)。
  2026-10-24 時点: 9/22 の週 3.96(画面の値から)、9/29 の週 1.91(記録から)、今週(途中)1.43(画面の値から)。ほかは既定値。
- サブスクリプションの上限がこの式どおりに消費されるかは公表されておらず、近似値として扱う。上限の大きさは時期で変わる前提とする
  (ユーザー)。常に同じこの種の説明は、レポートには書かない(§9)。
- サブエージェントの使用量は、呼び出し元のセッションのプロジェクトに含める。
- 同じ応答が複数行に分かれて記録される(途中の行は 0)ため、`(message.id, requestId)` ごとに出力トークンが最大の行を使う。
- 高速モード(2 倍の単価)や、長いプロンプトで単価が上がるモデル(Haiku 5.5 の 10 万トークン超)の割増は数えない(未対応)。

## 7. 保存するデータ(`state.json`)

データベースは使わず、取得元から消えると困るものだけを `data_dir/state.json`(数 KB)に残す。

```json
{
  "weeks": {"2026-10-20T10:00:00Z": {"final_pct": 69, "pdf": "~/Documents/Claude_Usage/Claude_Usage_2026-10-20.pdf"}},
  "slots": {"PokemonChampioons_Adviser": 0, "PirateGame": 1},
  "prices": {"claude-opus-6": [["2026-11-01T01:00:00+00:00", [6.0, 7.5, 12.0, 0.3, 30.0]]]}
}
```

- `weeks`: 作成済みの週(キーは週の終わり、UTC)。二重に作らないためと、前週の記録がデスクトップの記録から消えた後の前週比のため。
- `slots`: プロジェクトの色枠。週をまたいで同じ色にするため。
- `prices`: 費用の記録から推定した単価(モデル ID → [この時刻から, 5 つの単価])。§2.12。
- state.json のほかに、取得元から消える・ほかに残らない記録を data_dir に残す(2026-10-28、§2.13):
  - `plan-usage-archive.json`: デスクトップアプリの使用率の記録のコピー(アプリの記録の version 1 と同じ形。1 年で 1〜2 MB 程度)。
  - `activity-layout.json`: 活動の再生画面の配置の記憶(プロジェクトの位置・星雲の種類・セッションの相対位置。§2.15)。
  - `claude-code-usage.jsonl`: Claude Code の /usage の値(1 行 1 回: 時刻・全体%・5 時間枠%・モデル別%・製品別の内訳。
    取れなかった回は時刻と理由)。
- `axis`: 使用量(ドル)の縦軸の上限(`week_total` = これまでの週の合計の最大値、`window` = これまでの 5 時間枠の最大値、
  `models` = モデル別の週の合計の最大値)。新しい週で上限を超えたら、その週以降のレポートの上限を上げる
  (作成済みのレポートは作り直さない。ユーザーの指定)。`cu report --all` のときだけ、全週の最大値で全レポートをそろえる。
- レポートの PDF は `pdf_dir` に `Claude_Usage_<リセット日>.pdf`。元の HTML は一時ファイルで、残さない。
- PDF 変換のヘルパーは `data_dir/helpers/html2pdf`(ソースが新しくなれば作り直す)。

## 9. レポート(PDF。元は HTML)

まず単一の HTML ファイル(SVG・CSS・ツールチップ用の小さな JS を埋め込み、外部 CDN は使わない)を作り、それを PDF に変換する。

- 毎週のレポート: `~/Documents/Claude_Usage/Claude_Usage_<リセット日 YYYY-MM-DD>.pdf`(設定 `paths.pdf_dir`)。
  元の HTML は一時ファイルで、残さない。
- PDF への変換: macOS 標準の WebKit で印刷する小さな Swift のヘルパー(`render/html2pdf.swift`)を使う。
  - 新しいパッケージやブラウザは使わない。初回に `xcrun swiftc` でビルドし、`data_dir/helpers/html2pdf` に置く(ソースが新しくなれば作り直す)。
  - A4 縦。印刷用の CSS(`@media print` / `@page`)で、ダークモードの環境でも常にライトの配色にし、
    見出しとグラフのまとまり(`.keep`)の途中で改ページしない。折りたたみの表とツールチップは PDF には出さない。
  - ダミーデータでは 2 ページ(1 ページ目: KPI と週次上限のグラフ、2 ページ目: 5 時間枠・プロジェクト別・注記)。1 回の変換は約 1.5 秒。
- ダミーデータでの確認は `cu demo-report --pdf` で行う(§12.2)。

  - 週の使用量:
    - Claude Code の使用量(API 換算額 × 倍率、ドル)の累積を、なめらかな線で描く(2026-10-23、ユーザーの指定。それまでは階段線)。
      使った 5 時間枠ごとに始まりと終わりの 2 点を取り、単調な 3 次補間(Fritsch–Carlson 法)でつなぐ。
      枠の中でなめらかに増え、使っていない間は横ばいになる(行き過ぎて値が戻ることはない)。
    - 濃い線が全体(左軸)、薄い線が `report.models` のモデル(Fable、右軸)。
    - 2 つの縦軸はユーザーの指定(2026-10-23。当初は同じ縦軸だった)。読み違いを減らすため、左右とも上限の 4 等分で横線をそろえ、
      両軸の上に見出し(「全体」「Fable」)、凡例に「全体(左軸)」「Fable(右軸)」と書く。
    - 各軸の一番上は、これまでの最大値ちょうど(`axis.week_total` / `axis.models`)。きりのよい値への切り上げはしないので、
      目盛りの値は半端になる(モデルの倍率を入れた後の値は、作り直したレポートの軸を見る)。
    - 値は十字線で両方読める(線の終わりの値のラベルは、右軸の目盛りと重なるため付けない。合計は KPI にある)。
  - 週次上限の使用率(記録が十分な週だけ): 週次上限 %(0–100 固定)の線。記録のある「時」が `min_limit_hours`(24)以上の週だけ載せる。
    足りない週は注記に「◯ 時間分しかないため載せていない」と書く(最終の値は KPI、一覧は折りたたみの表)。
    2026-10-23 時点で載るのは 9/22〜9/29(39 時間分)と 9/29〜10/6(27 時間分)の週だけ。

    それまでは、次の記録まで値を保つ階段線)。記録と記録の間は補間なので、実際の増え方とは限らない。値が下がる区間(手動リセット)も
    行き過ぎずに下がる。記録点が `marker_max_points` 以下なら点も描く。
    十字線とツールチップで各記録の値と時刻を読める。
    - モデル別の週間上限の %(Claude Code の /usage の記録と画面の値、§2.13)がある週は、`report.models` のモデル(Fable)の線を
      薄い色で重ねる(2026-10-28、ユーザーの指定。「参考値」とは書かない)。どちらもそれぞれの上限に対する % なので同じ軸で読める。
      凡例「全体」「Fable」、線の終わりの値(近ければ縦にずらす)、十字線のツールチップにその時点の Fable の値、
      折りたたみの記録の表に Fable の列(記録の時刻が違うので、ない欄は --)を出す。
    - 当初案の「均等ペース」の点線は、ユーザーの指定で削除した(2026-10-23)。
  - 下段: 5 時間枠ごとの棒(ユーザーの指定、2026-10-23)。左軸の一番上は、これまでの 5 時間枠の最大値ちょうど(`axis.window`、2026-10-23 時点で 6,300 万)。
    目盛りは 4 等分(右軸の 0/25/50/75/100% と横線がそろう)。
    - 棒: その枠の使用量(左軸、ドル。見出しは「換算額」)。プロジェクト別に積み上げ、円グラフと同じ色を使う。棒は枠の時間帯の中央に置く。
    - ●: その枠のリセット直前の 5 時間枠の使用率(右軸、0–100%)。記録がない枠には出さない。
    - 縦軸は 2 つ(左: トークン、右: 5 時間枠の使用率)。ユーザーの指定による。dataviz の指針では 2 軸は避けるとされているため、
      左軸の目盛りをちょうど 4 等分にして右軸の 0/25/50/75/100% と同じ横線にそろえ、両軸の上に見出しを付けて読み違いを減らす。
    - 棒・● ともにツールチップあり。● は小さいので、直径 24 の透明な当たり判定を重ねる。
  - 上限%を 1 点も取得できなかった週は、上段に「この週の上限%の記録はありません」と表示する。
- 円グラフはドーナツ型にし、中央に週の合計を表示する。上位 `max_slices` 件に入らないもの、
  または `others_min_pct` 未満のものは「その他」(灰色)にまとめる。
- Claude Code 以外の利用(§2.10)がある週は、円グラフと表にその割合の区分を加え、プロジェクトの割合を週全体に対する値に直す
  (2026-10-23)。色は「その他」と見分けられる濃い灰色(`--noncode`。dataviz の検証スクリプトで隣の色との差を確認)、
  推定した値は名前に「(推定)」を付ける。中央の値は Claude Code の合計のままで、見出しを「Claude Code 分」にする。
  表の使用量・セッションは「--」。時系列のグラフと KPI の「最多」は Claude Code だけ(見出しに「(Claude Code)」)。
  Claude Code 以外の区分が 2 つ以上(チャット・Cowork など)のときは、隣り合っても見分けられるよう濃い灰色と中くらいの灰色を
  交互に使う(`--noncode` / `--noncode-2`。2026-10-28、検証スクリプトで隣の色との差 16 以上を確認)。
- 開発時間(§2.14): KPI の 4 つ目の欄に週の合計と最も長かったプロジェクト、プロジェクト別の表に列を出す(2026-11-01、ユーザーの要望)。
  表の Claude Code 以外の区分は「--」。
- 常に同じ仕様の説明(グラフの読み方、近似値である旨、週・5 時間枠の区切り方、記録の取れる条件など)はレポートに載せない
  (2026-10-23、ユーザーの指定)。注記には、週ごとに変わる事実(記録点数、手動リセット、記録が足りない旨など)だけを書く。
- 色は dataviz の参照パレット(分類 8 色、ライト/ダークで検証済み)を使う。プロジェクトへの割り当ては、
  過去の週で使った枠があればそれを引き継ぎ(フェーズ 1 で DB に保存)、なければ空いている枠を番号順に使う。
  - 番号順に並べたとき隣同士が見分けやすいよう検証された並びなので、大きい順に割り当てると円グラフで隣り合う区分が見分けやすい。
  - 当初案の「名前のハッシュで固定」は、表示確認で水色と緑が隣り合って見分けにくかったため変更した。
- 値はすべて表でも読める(プロジェクト表は常に表示、5 時間枠ごとの表と上限%の記録は折りたたみの表)。
- 幅 600px 以下では、時系列のグラフを最小幅 560px にしてカード内で横スクロールさせる(文字が小さくなりすぎないため)。
  ページ全体は横にはみ出さない。
- 通知: `osascript -e 'display notification …'` で 1 行の要約(例「先週 78% 使用 / 最多 transcription 66%」)を出す。
  - `osascript` の通知はクリックしてもファイルを開けない。PDF は `~/Documents/Claude_Usage` から開く。
  - クリックで開く通知にするには `terminal-notifier` などの追加が必要になる。新しい依存なので、採用する場合は別途確認する。

## 10. 自動実行(2026-10-23 に適用)

- launchd の LaunchAgent `~/Library/LaunchAgents/local.claude-usage.tick.plist` が、ログイン時と 30 分ごと(設定 `[schedule]`)に
  `cu tick` を低優先度(Background・LowPriorityIO・Nice 10)で動かす。内容をユーザーに提示し、承認を得て適用した。
  - 作り直し・外し方: `cu schedule`(内容の表示のみ)/ `cu schedule --apply` / `cu schedule --remove`。
  - ログ: `~/Library/Application Support/claude-usage/logs/tick.log`(何か起きたときだけ 1 行ずつ書く)。
- `cu tick` の 1 回分(何もなければ約 0.8 秒):
  1. 終わった週のうち未作成の週のレポート(PDF)を作り、通知する(火曜 19:00 のリセット後、遅くとも 30 分以内)。
     会話ログが更新されていれば、活動の再生画面も 60 分ごとに作り直す(§2.15。失敗してもログに書くだけ)。
     失敗したらログに書き、同じ失敗の通知は `repeat_hours` の間は繰り返さない。
  2. デスクトップアプリの使用量の記録(plan-usage-history.json)の最新が `stale_minutes`(60 分)より古ければ、

     - 2026-10-27 変更(ユーザーの指定): 止まった原因がメニューを開けば直るもの(最後に開いてから 24 時間の期限切れ)か、
       アプリが起動していないときだけ通知する。Mac のスリープや通信の失敗で一時的に止まっただけなら、起きれば自動で
       再開するので出さない(10/26 8:16 に、夜の間スリープしていただけで「13 時間止まっています」と出ていた)。
     - 通知は `active_from_hour`〜`active_until_hour`(8〜23 時)の間だけ、`repeat_hours`(6 時間)に 1 回まで。
     - Claude のアプリが起動していなければ、起動を促す文面にする(`ps` で本体のプロセスを確認)。
     - 記録は止まってから知らせるので、開くまでの間(最大で 60 分 + 30 分程度)は抜ける。→ 3 を加えた。
  3. 記録が止まる前の通知(2026-10-24 追加、ユーザーの指定): 使用量メニューを最後に開いてから `tray_notice_hours`(20 時間)
     経ったら、「◯/◯ ◯:◯ に使用量の記録が止まるので、それまでに使用量のメニューを開いてください」と通知する。

       書き換えない。設定 `[paths] app_config`。
     - アプリが記録を続けるのは最後に開いてから `tray_window_hours`(24 時間。アプリのログ
       「poll requires tray open within 86400000ms」)。止まる時刻を過ぎたら出さない(2 の通知に任せる)。
     - 20 時間後が通知しない時間帯(23〜8 時)に入り、記録が朝 8 時より前に止まるときは、その夜の 22 時に早める

     - メニューを開くたびに 1 回だけ(state.json の `tray_reminded_for` に、通知した回の最後に開いた時刻を残す)。
       2 の通知を出した回には重ねない。
     - 2026-10-24 の実機での確認: 最後に開いたのは 10/24 08:54 → 止まるのは 10/25 08:54 → 20 時間後の 04:54 は夜なので、
       10/25 8 時の回で通知する予定(通知は未発火。テストで確認)。
  4. 通知は Mac を操作している間だけ出す(2026-10-27 追加、ユーザーの指定)。最後の操作(キーボード・マウスなど)からの時間を
     `ioreg` の `HIDIdleTime` で読み(権限は要らない、約 0.02 秒)、`[notify] active_idle_minutes`(10 分)以内なら操作中とみなす。
     - 操作していないときは出さず、次の回に持ち越す。レポートの通知は state.json の `pending_notices` に残して次に出し、
       記録の通知は出したことにせず次の回に判断し直す(その間に記録が再開すれば出さない)。
     - きっかけ: 10/24 21:11・10/25 8:17・9:47 の通知が、蓋を閉じた Mac の一時的な起動(画面は消えたまま)の間に出て、
       ユーザーの目に入らなかった。
  0. 最初に Claude Code に /usage の値を問い合わせて記録する(2026-10-28 追加、§2.13)。取れなくてもログに書くだけで通知しない。

| PDF の変換に Xcode のコマンドラインツールが必要 | ツールがないとヘルパーをビルドできない | 初回だけビルドしてバイナリを data_dir に置く。失敗したら HTML だけ保存して通知で知らせる |
| 5 時間枠の区切り方(最初に使った時刻の「時」から 5 時間)(未確認) | 記録のない時間帯の枠の位置がずれる | 記録がある枠は `fh` の下降で決める。記録がない時間帯だけトランスクリプトの利用時刻から推定する |
| 上限の消費量の計算式は非公表。モデルで約 4 倍違い、時期でも変わる(§2.8) | トークン量と週次の使用率は一致しない | モデルの倍率を入れた(§6)。トークン量は使い道の比較に使い、上限に対する状況は使用率の記録で見る |
| Fable の倍率 4 は推定値で、公表されていない(§2.9) | 時期やモデルの版で変わりうる | 記録が十分な週はその週の推定値を使う(§2.11)。足りない週は設定の既定値 |
| 単価の変更・新しいモデル | 単価表が古くなる | Claude Code の費用の記録から自動で推定する(§2.12)。高速モードや長いプロンプトの割増は数えない |
| 活動の再生画面の関係の線はデスクトップアプリのセッション情報や会話ログの内部の項目に頼る(§2.15) | 項目が変わると線が減る | 取れない項目は関係なしとして扱い、画面は動き続ける |
| 開発時間は応答の時刻からの近似(§2.14) | 区切りの間隔で値が変わり、自動で動いた分や Claude Code の外の作業は正しく表せない | 同じ区切りで比べるための値として出す。間隔は設定で変えられる |
| トランスクリプト形式の変更 | 取り込みが失敗する | 寛容に解析し、失敗した行数をレポートに出す。fixture テストで検知する |
| トランスクリプトの自動削除(保持期間は未確認) | レポートを作る前に消えると欠損する | 週が終わったら早めに `cu report` を動かす(§10) |
| Claude Code 以外の利用(Cowork・チャット)の使用量が分からない | 円グラフが Claude Code だけになる | Cowork は割合で加える(手入力・推定、§2.10)。推定は同時に使った分を数えないので少なめ。チャットは 5% 以下として扱わない |

## 14. 公開(2026-11-03)

ユーザーの要望: GitHub で公開する。最終的にはポートフォリオの 1 つとして出すが、ポートフォリオは別に作るので、
このリポジトリは単体で見られる形にし、ポートフォリオの中には取り込まない。非公開のリポジトリのプロジェクト名が見えるのは問題にしない(ユーザー)。

| 項目 | 決定 |
|---|---|
| 公開の範囲 | このリポジトリを public にし、README に画面写真とデモへのリンクを載せる |
| ライセンス | MIT(ユーザーの選択) |
| コミットの作者のメール | 個人のアドレスから GitHub の noreply のアドレスに、履歴ごと書き換える(ユーザーの選択)。以降はリポジトリの設定(`git config --local user.email`)で noreply を使う |
| 書き換えた履歴の送り方 | 元のリポジトリを `Claude-usage-old` に改名して非公開のまま残し、同じ名前で作り直したリポジトリに送った(ユーザーの選択)。元のリポジトリに強制プッシュすると、アクティビティの画面から書き換え前のコミットにたどり着ける可能性があるため(未確認) |
| 画面写真 | 実際の記録で撮る(ユーザーの選択)。週次レポートは 10/27 に終わる週の PDF、再生画面は 10/30 23:00 の場面 |
| 再生画面のデモ | GitHub Pages で公開する(ユーザーの選択)。実際の記録から作った HTML を `gh-pages` ブランチに置く。GitHub への送信を定期実行に入れないため、自動では更新しない |

- 公開前の点検: 全履歴(7 コミット)を調べ、API キー・トークン・秘密鍵らしい文字列はなかった。個人の情報は、コミットの作者のメール、
  テストの中のホームのパス(`/Users/kenta/...`)、プロジェクト名。メールは書き換え、ほかはユーザーの判断でそのままにした。
- 再生画面に埋め込むデータ: プロジェクト名・セッションの開始時刻・15 分ごとの応答数・関係の種類・日ごとの応答数と API 換算額。
  パス・ブランチ名・ファイル名・会話の本文は入らない(確認済み)。
- 画面写真の撮り方: 再生画面は、時刻を止めて星雲の焼き付けを済ませた写しを、ヘッドレスの Chrome(1600×1000)で撮った。
  PDF は PDFKit でページを 2 倍の画像にし、上から切り出した。一度きりの作業なので、手順のスクリプトはリポジトリに置かない。
- デモの更新は手動: `cu activity --out` で作った HTML を `index.html` として、`Claude_Usage_Activity.version.js` と一緒に
  `gh-pages` ブランチに入れてプッシュする。
